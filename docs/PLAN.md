### Phase 5.UV — Plugin-side signature verification (committed 2026-04-23)

Architectural commitment (session 17): both `pbRequestSignature` verification *and* UV-response signature verification migrate from sidecar-side to plugin-side, so the plugin trusts the sidecar for **no** security-critical claim. Rationale: passes third-party / KeePass-community security review cleanly; avoids the asymmetry trap of verifying one signature plugin-side and the other sidecar-side.

Design findings backing this plan:
- Microsoft PasskeyManager sample (`Windows-classic-samples/Samples/PasskeyManager/cpp/PluginAuthenticator/PluginAuthenticatorImpl.cpp:578-605`) proves v1 UV signature verification is feasible with `WebAuthNPluginGetUserVerificationPublicKey` over `SHA-256(pbEncodedRequest)`. We use `EXPERIMENTAL_WebAuthNPluginPerformUserVerification2` instead so both signatures share the op-sign pubkey cache (one cache plugin-side, not two).
- `EXPERIMENTAL_WEBAUTHN_PLUGIN_USER_VERIFICATION_REQUEST_2` is declared in `microsoft/webauthn`'s public `webauthnplugin.h` (**not** NuGet-only as earlier memory claimed): 48 bytes = v1's 32 bytes + `DWORD cbBufferToSign` + `PBYTE pbBufferToSign`. Response remains an opaque `PBYTE*` signature buffer.
- De-risk ordering: shared plugin-side plumbing first, simpler stable-API migration (`pbRequestSignature`) second, experimental API + dialog UX (`_2` UV) third. If stable-API migration works end-to-end, UV is a small delta.

Zero one-shot plugin-side state to break on a second handshake within the same plugin process lifetime. **`SHARED_STATE` lifecycle in retry — the key correctness point:** `SHARED_STATE` is `Mutex<Option<Arc<Mutex<State>>>>` (exe_server.rs:74). The in-flight dispatch holds its own `Arc` clone (call it Arc1) of the same allocation `SHARED_STATE` points to; `reconcile_vault_with_os` (exe_server.rs:331-517) also holds an Arc clone. **Retry success path** must NOT touch `SHARED_STATE` — it just reconnects + re-RPCs and lets the existing `obj.state.lock().pipe = Some(pipe_back)` at server.rs:470 store the fresh pipe back into Arc1. `SHARED_STATE` keeps pointing at Arc1 (now repaired); the next activation reuses it.
